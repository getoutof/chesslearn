# Как вносить изменения

Стандарты для веток, коммитов и pull request'ов в ChessLearn.

## Главное правило

**Один PR — одна цель.** Ревьюер должен за несколько минут понять, что изменилось, зачем
и на что смотреть. Если в описании PR хочется написать «а ещё…» — это отдельный PR.

## Задачи

- Работа начинается с задачи в [Issues](https://github.com/getoutof/chesslearn/issues).
  Если задачи нет — сначала заведите.
- PR ссылается на задачу: `Closes #N`, если PR её завершает, или `Part of #N`, если это шаг.
- Решения (почему выбрали так, а не иначе) записываются в задачу или в PR, а не теряются в чате.

## Ветки

`<тип>/<коротко-о-чём>`, латиницей через дефис:

| Тип | Когда |
|---|---|
| `feat/` | Новая функциональность |
| `fix/` | Исправление ошибки |
| `chore/` | Конфиги, зависимости, обновления, сгенерированный код |
| `ci/` | GitHub Actions |
| `docs/` | Только документация |
| `tool/` | Скрипты для разработки |
| `refactor/` | Переделка без изменения поведения |

Пример: `feat/hotseat-game`, `fix/castling-rights`.

## Коммиты

- **Заголовок** на английском, в повелительном наклонении, до 72 символов:
  `Add dev and prod flavors`, а не `added flavors` и не `fixes`.
- **Тело** — *зачем*, а не только *что*. Что изменилось, видно в диффе.
- Один коммит — одно логическое изменение. Особенно для конфигов: одна правка конфига —
  один коммит с причиной в сообщении.
- Не смешивайте в одном коммите форматирование и изменение логики.

## Комментарии в коде

Комментарии пишем **по-русски** — в Dart, Kotlin, Swift, YAML, shell, во всём коде, который
пишем сами. Английские термины и идентификаторы внутри можно: «подпись для flavor prod»,
`` `flutter pub get` ``. Сгенерированный код (`flutter create`, `*.g.dart`, `*.freezed.dart`
и т.п.) не трогаем — там остаётся как есть.

Проверяет `dart run tool/check_comments.dart` (в CI — на каждый PR):

- `lib/`, `test/`, `tool/`, `.github/`, `analysis_options.yaml` — наши целиком, проверяются полностью;
- `pubspec.yaml`, `android/app/build.gradle.kts`, `android/gradle.properties`, нативный код
  в `android/app/src/main/kotlin/` и `ios/Runner/` — созданы из шаблона Flutter, в них
  остаются его английские комментарии. Поэтому проверяются только строки, изменённые в PR
  (`--base <ветка>`);
- соседние строки комментария проверяются вместе, как один абзац; комментарий проходит, если
  в нём есть русский текст. Директивы (`// ignore: …`, `# shellcheck …`) не проверяются.

Новый наш каталог или файл из шаблона, который мы правим, — добавьте в `ownPaths` или
`mixedPaths` в `tool/check_comments.dart`.

## Размер PR

- Рукописных изменений — ориентир **до ~400 строк**. Больше — разбейте.
- **Сгенерированный код — отдельным PR, без правок.** Например, результат `flutter create` или
  миграции: в описании — точная команда, которой он получен. Свои изменения — следующим PR.
- Исключение — код от `build_runner` (`*.g.dart`, например таблицы drift): он меняется вместе
  со своим исходником, поэтому идёт в том же PR, но **отдельным коммитом**
  (`Regenerate drift code`). Его не ревьюят построчно: CI перегенерирует его и проверяет,
  что он совпадает с закоммиченным.
- Если шаги зависят друг от друга — цепочка PR (см. ниже), а не один большой.

## Описание PR

Пишется по шаблону (подставляется автоматически), на русском:

- **Что** — кратко, списком;
- **Зачем** — какую проблему решает, ссылка на задачу;
- **Как ревьюить** — на что смотреть в первую очередь, что можно пропустить;
- **Как проверено** — команды, устройства, CI; для UI — скриншот;
- **Чек-лист**.

## Конфиги

Конфиги легко пропустить на ревью, поэтому:

- каждое изменение конфига объясняется в коммите и в PR;
- карта конфигов [`docs/CONFIG.md`](docs/CONFIG.md) обновляется **в том же PR**: зачем файл, кто
  им управляет, можно ли менять, отличается ли для dev/prod;
- файлы, которыми управляет Flutter (`.metadata`, `*.xcworkspace`, `Debug/Release.xcconfig` и др.),
  вручную не правим — только через `flutter upgrade` / `flutter create .`;
- **dev и prod**: если меняется что-то, что отличается между ними (id, название, подпись, адреса API),
  — проверить оба flavor'а.

## Проверки перед ревью

- `dart format lib test tool`, `flutter analyze` — без замечаний, `flutter test` — зелёный;
- поменяли таблицы drift или другой исходник кодогенерации —
  `dart run build_runner build --delete-conflicting-outputs`, результат закоммитить;
- `dart run tool/check_comments.dart --base origin/main` — комментарии на русском;
- CI в PR зелёный;
- изменения в `ios/` проверены сборкой на macOS (CI собирает iOS dev и prod);
- изменения в `android/` проверены сборкой (локально или `tool/remote.sh`);
- новая логика — с тестами.

## Зависимости, ассеты, лицензии

Код распространяется под GPL-3.0 (см. [README](README.md#лицензия)).

- Новая зависимость: проверить, что лицензия совместима с GPL-3.0, и добавить её в
  [`THIRD_PARTY.md`](THIRD_PARTY.md) в том же PR.
- Новый ассет (фигуры, звуки, шрифты, тексты): источник, автор и лицензия — в `THIRD_PARTY.md`.
  Ассеты с ограничениями NC/ND не используем.

## Секреты

В репозиторий **никогда** не попадают ключи подписи, пароли, токены и личные настройки
(`android/key.properties`, `*.jks`, `tool/remote.env` и т.п.). Для CI — GitHub Secrets.
Если секрет всё-таки попал в коммит, — он считается скомпрометированным: перевыпустить, а не
только удалить из истории.

## Цепочки PR

Когда изменения зависят друг от друга:

1. каждый следующий PR открывается от ветки предыдущего (base = ветка предыдущего PR);
2. в описании каждого — вся цепочка и её порядок;
3. мёржатся строго по порядку;
4. после мёржа предыдущего PR — база следующего переключается на `main`.

## Ревью и мёрж

- PR мёржит владелец репозитория после ревью.
- Замечания ревью — отдельными коммитами, чтобы было видно, что изменилось. Если замечание
  меняет подход целиком — PR можно закрыть и открыть заново, ответив на замечания в старом.
- Способ мёржа — **Create a merge commit** или **Rebase and merge**. **Squash** не используем:
  теряется история по коммитам и ломаются цепочки PR.
- После мёржа ветка удаляется.

### Что закреплено в настройках репозитория

| Настройка | Значение |
|---|---|
| Способы мёржа | merge commit и rebase; **squash отключён** |
| Ветка после мёржа | удаляется автоматически; следующий PR цепочки переключается на `main` сам |
| `main` | изменения **только через PR**, в том числе для администраторов |
| `main` | запрещены force push и удаление |
| Обсуждения в PR | все треды ревью должны быть закрыты (resolved) до мёржа |
| Одобрение ревьюером | не требуется: PR создаются от аккаунта владельца, а свой PR GitHub одобрить не даёт |
| Обязательный CI | перед мёржем в `main` должны пройти `Analyze & test`, `Build Android APK (dev)`, `Build iOS (dev, no codesign)`, `Build iOS (prod, no codesign)`; засчитываются только проверки от GitHub Actions |
| Актуальность ветки | ветка PR должна содержать свежий `main` (кнопка **Update branch**); после мёржа предыдущего PR цепочки следующий нужно обновить |
